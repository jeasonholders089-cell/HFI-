## 一、一句话概览

一个**单库两表**的 Postgres：`children`（问卷 + AI 结果）、`app_meta`（键值小仓库，目前只放词云缓存）。
**表结构极其简单，复杂度全在 JSON 字段和"场次"这个推导概念上。**

| 项 | 事实（2026-09-18 实测） |
| --- | --- |
| 数据库 | PostgreSQL **15.15**（Debian 包） |
| 库名 | `hfi` |
| 服务器时区 | **`Etc/UTC`** ← 这条决定了很多事，见第六节 |
| 本地地址 | `postgres://…@127.0.0.1:5434/hfi`（`src/.env` 的 `DATABASE_URL`，**端口是 5434 不是 5432**） |
| 托管环境 | 平台供给的托管 Postgres，连接串由平台注入（带 `sslmode=require`，见 `lib/pg-dsn.ts`） |
| 访问方式 | 业务代码一律 `lib/db.ts` 的 `getDb()`；**禁止 `new Pool`、禁止手写 DDL** |
| 迁移工具 | drizzle-kit，版本化 SQL 在 `src/drizzle/`（4 个迁移） |

## 二、`children` —— 问卷与 AI 结果

一个孩子一行。**15 列**（实测的物理顺序如下，注意 `submission_key` / `created_at` 在最后——
这是迁移追加的结果，与 `schema.ts` 的声明顺序不同，不影响使用）。

| # | 列名 | 类型 | 可空 | 默认 | 含义 |
| --- | --- | --- | --- | --- | --- |
| 1 | `id` | integer | 否 | `nextval(children_id_seq)` | 主键，**自增** |
| 2 | `english_name` | text | 否 | — | 孩子的**英文名（昵称性质，不要求真名）** |
| 3 | `age` | integer | 否 | — | 年龄（应用层校验 1–100） |
| 4 | `dream_school` | text | 否 | — | 梦想学校，**自由文本**，可能多所（顿号/逗号分隔） |
| 5 | `interests` | text | 否 | — | 兴趣，自由文本 |
| 6 | `activities` | text | 否 | — | 喜欢的活动，自由文本 |
| 7 | `self_description` | text | 否 | — | 孩子自我描述，自由文本 |
| 8 | `parent_observation` | text | 否 | — | 家长观察，自由文本 |
| 9 | `dream_career` | text | 否 | — | 梦想职业（**选填，空串不是 NULL**） |
| 10 | `created_at` | timestamptz | 否 | `now()` | 创建时间。**"场次"就是从它推导出来的**（第六节） |
| 11 | `ai_directions` | text | **可空** | — | AI 输出的三个学术方向，**JSON 字符串**（第四节） |
| 12 | `ai_traits` | text | 可空 | — | **历史残留，已无写入方**（第八节） |
| 13 | `ai_summary` | text | 可空 | — | **历史残留，已无写入方**（第八节） |
| 14 | `submission_key` | text | **可空** | — | 幂等键（UUID）。家长端每次提交带一个，**防刷新重复提交** |

**约束与索引**（实测）：

```
children_pkey                  PRIMARY KEY (id)
children_submission_key_unique UNIQUE (submission_key)
```

> **注意**：`submission_key` 可空 + 唯一 → **批量导入不写它**（`NULL` 在 Postgres 的唯一索引里不互相冲突，
> 所以可以有很多行都是 NULL）。这是"Excel 导入能成功、又不会被幂等键挡住"的前提。

### 谁读谁写

| 接口 | 动作 |
| --- | --- |
| `POST /api/children`（家长自助） | 插 8 个问卷字段 + `submission_key`；随后**同一条记录**回写 `ai_directions`（AI 失败则留空，返回 202） |
| `POST /api/children/bulk`（批量文本 / Excel） | 只插 8 个问卷字段（**不写 `submission_key`，也不跑 AI**） |
| `POST /api/children/analyze` | 读 7 个字段（除英文名）→ 写 `ai_directions`。**有 3 个方向但类别非法时只重分类**，不重新生成方向 |
| `GET /api/children/summary` | 全字段读 + 聚合（方向统计、梦想院校人次与坐标） |
| `POST /api/children/wordcloud` | 只读 6 个字段（`id/age/interests/activities/self_description/parent_observation/dream_career`）——**不含姓名、不含梦想学校** |
| `DELETE /api/children/[id]` | 删一行（**校验同源**） |
| `POST /api/children/clear` | **删全表**（校验同源） |

## 三、`app_meta` —— 键值小仓库

建库时就有的通用表，**2026-09-18 起第一次真正被使用**（之前完全没用）。

| # | 列名 | 类型 | 可空 | 默认 | 含义 |
| --- | --- | --- | --- | --- | --- |
| 1 | `id` | integer | 否 | `nextval(app_meta_id_seq)` | 主键 |
| 2 | `key` | text | 否 | — | 键，**唯一** |
| 3 | `value` | text | 可空 | — | 值（文本；JSON 就存字符串） |
| 4 | `created_at` | timestamptz | 否 | `now()` | 创建时间。**注意：覆盖写不会更新它** |

```
app_meta_pkey       PRIMARY KEY (id)
app_meta_key_unique UNIQUE (key)
```

**目前只放一种东西**：词云缓存，键 `wordcloud:<场次>`（如 `wordcloud:2026-09-18`），
值是 `{groups:[{word,count}], total, generatedAt, model}`。
写入用 `onConflictDoUpdate({target: key})`（同场次覆盖），实现见 `lib/wordcloud-cache.ts`。

## 四、JSON 字段的形状契约（`ai_directions`）

**这一列是 text，不是 jsonb**——数据库不管它的形状，形状靠应用层写死。
实测**历史上有两种形状并存**，读的时候要有心理准备：

| 来源 | 元素形状 | 备注 |
| --- | --- | --- |
| 现在的三个 prompt（`/api/children`、`/api/children/analyze` 两条分支） | `{category, name, nameEn, reason}` | 服务端**逐字段校验**：四个都得是非空字符串，且 `category` ∈ 8 类 |
| 更早的版本（9/16 那批历史记录） | `{category, name, reason, nearTerm, usPath}` | 没有 `nameEn`，多了两个字段。页面读 `nameEn` 时会空着 |

实际内容（取一条 9/16 的历史记录）：

```json
{
  "category": "自然科学",
  "name": "计算机科学",
  "nameEn": "Computer Science",
  "reason": "喜欢用编程实现自己的想法",
  "nearTerm": "独立做一个小游戏",
  "usPath": "AP Computer Science A"
}
```

**三条纪律**：

1. **恰好 3 个元素**——产品定义就是三个学术方向，多一个少一个都算"没有画像"（`lib/child-profile.ts`）；
2. `category` 必须是 8 类之一，否则算**"有画像但未分类"**——它不进方向统计，页面上会提示「AI 补全分类」；
3. **不要假设元素里一定有 `nameEn`**——历史数据没有。要新增字段时，读的地方一律按可选处理。

## 六、场次：一个**没有字段**的概念

"一天一场"是产品口径（`docs/10` §3.7），但**数据库里没有 `session` 列**——
场次是查询时**从 `created_at` 现算**的。见 `lib/school-session.ts`。

```
场次 = created_at 落在北京时间某一天的自然日内
区间 = [当日 00:00+08:00, 次日 00:00+08:00)   ← 左闭右开
```

**为什么不用 `date(created_at) = current_date`**：实测这台库的服务器时区是 **`Etc/UTC`**。
活动早上 8 点录入，UTC 还是**前一天 24 点**——用数据库的"今天"会把整场算到昨天去，
大屏开场就是空的。所以日界在**应用层手算**，固定 `+08:00`（中国不实行夏令时，不需要时区库）。

**代价与边界**（知道就行）：

- **跨零点的活动会被切成两场**；
- **同一天的两个独立活动会合并成一场**。将来真要一天多场，加一列 `session` 即可（加列不影响已有数据）；
- 没有 `created_at` 的索引——按场次查是全表扫。**几十到几百行完全无所谓**，等活动数据上千再考虑加。

## 七、迁移与纪律（改表之前必读）

**唯一真源是 `src/db/schema.ts`。** 改表结构的完整流程：

```bash
cd src
# 1. 改 db/schema.ts
# 2. 生成版本化 SQL（只读 schema.ts，不连库）
pnpm exec drizzle-kit generate
# 3. 自己读一遍生成的 SQL —— 尤其是删列/改类型，migrate 会忠实执行它
# 4. 与代码一起提交
```

四条硬规矩（`AGENTS.md` 第六节）：

1. 表结构**只在** `db/schema.ts` 声明，业务代码经 `getDb()` 读写；
2. **禁止手写 `CREATE` / `ALTER` SQL**，也禁止 `IF NOT EXISTS` 这类幂等技巧；
3. 应用与发布**只 apply 已生成的迁移**（平台按 `compose.yaml` 的 `luffy.migrate` 跑 `drizzle-kit migrate`）；
4. **禁止 `drizzle-kit push` 打生产**——它是开发期 sync，`--force` 会静默删列毁数据。

现有迁移（4 个，逐个读过）：

| 文件 | 干了什么 |
| --- | --- |
| `0000_init.sql` | 建 `app_meta`（id / key 唯一 / value / created_at） |
| `0001_red_molly_hayes.sql` | 建 `children` 的**最初 10 列**（8 个问卷字段 + id + created_at）——**没有 AI 结果列** |
| `0002_dizzy_omega_red.sql` | 给 `children` 加 `ai_directions` / `ai_traits` / `ai_summary` 三列（AI 结果起初就是这么加的） |
| `0003_nebulous_warlock.sql` | 加 `submission_key` 列 + 唯一约束（幂等提交） |

> 这也解释了第二节里"物理列顺序与 `schema.ts` 声明顺序不同"：`ai_*` 和 `submission_key` 都是后来 ALTER 加上去的，
> 自然排在 `created_at` 后面。

## 八、已知问题与注意事项

| # | 事项 | 现状 | 该怎么办 |
| --- | --- | --- | --- |
| 1 | `ai_traits` / `ai_summary` 两列**已无写入方** | 写库侧早就停了；`summary` 接口里聚合它们的死代码已于 9/17 删除 | **先留着不删**——删列对生产库不可逆。等 `/child/[token]` 画像页定型后一起决定 |
| 2 | `/api/children/summary` **未脱敏** | 它 `select *` 返回 `children: rows` 全字段，`english_name` 和 `ai_directions` 一起发到浏览器 | 一期决定不修（大屏不渲染姓名，但 devtools 能拿到配对）。**二期必须处理**——这是规范层面的缺口 |
| 3 | `/explore` 的「孩子表」第一列是 `interests` **自由文本** | 可能夹带学校/班级等可识别信息 | 同上，二期随画像页处理 |
| 4 | `age` 的 1–100 校验**只在应用层**，库里没有 CHECK 约束 | 直接写库能塞进 `-5` | 目前只有应用写库，可接受；要更严就加 CHECK（一次迁移） |
| 5 | `dream_career` 等的"选填"存的是**空串**不是 NULL | 批量导入/注册都写 `""` | 读的地方按空串判空（`isBlank` 已处理 `""`）；不要假设 NULL |
| 6 | `ai_directions` 是 text 不是 jsonb | 数据库不校验形状 | 形状契约见第四节；要查 JSON 内部得在应用层解析 |
| 7 | 没有 `created_at` 索引 | 每次按场次查都是全表扫 | 数据量小（几十~几百）无所谓；上千再考虑 |

## 九、怎么连、怎么查（本地）

**用 psql**（如果有）：

```bash
psql "postgres://postgres:...@127.0.0.1:5434/hfi"
\dt                      # 看表
\d children              # 看列与索引
select count(*) from children;
```

**用脚本**（仓库里已有现成的）：

```bash
cd src
pnpm exec tsx ../tmp/...      # tmp/ 里有若干一次性脚本，均不进版本库
```

**应用侧**：

```bash
cd src && pnpm dev            # 应用读 src/.env 的 DATABASE_URL
```

> 提醒：`src/.env` 是应用与脚本都读的那份；**仓库根目录如果还有 `.env`，应用是不会读它的**
> （曾把 `AI98_BASE_URL` 加在根目录、应用读不到，最后同步到 `src/.env` 才生效）。

## 十、数据合规（摘自 `AGENTS.md` 第五节）

- **不采集真实姓名、手机号、微信、身份证、照片**。`english_name` 是昵称性质，不要求真名；
- 公开页面（大屏、首页）**不得**出现"孩子姓名 + 个人画像"的组合；
- 单孩子画像页**不得**用可遍历的自增 ID（所以将来 `/child/[token]` 必须用随机 token，**不能用这里的 `id`**）；
- 删除类接口必须校验同源（`/api/children/clear` 与 `/api/children/[id]` 都是）；
- 数据只用于本次活动现场，不对外发布、不导出分发。
