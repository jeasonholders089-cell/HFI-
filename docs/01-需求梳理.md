## 一、已确认的前提

| # | 前提 | 影响 |
| --- | --- | --- |
| 1 | 产品有**两条并列的用户路径**：家长自己填写孩子信息、工作人员把访谈内容提交进系统 | 两条路径都是一等公民，都要做完整，最终产出同一份结果 |
| 2 | 这是一款**面向 C 端（家长）的产品** | 家长端的体验是生命线，不是"给内部用的采集工具" |
| 3 | 一期**暂不支持批量处理** | 不做批量导入、不做批量勾选操作界面；每条数据独立走完整链路 |
| 4 | 一期**没有管理后台**（当前没有运营角色） | 只做产品本身的五个页面：家长端 / 工作人员端 / 画像页 / 大屏 / 首页。数据问题在活动前彩排阶段解决 |
| 5 | 梦想院校由**家长自己填**（不做下拉清单，只在输入时给联想提示） | 保留真实表达；命中坐标表的才上图，没命中的保留原文、不阻塞提交 |
| 6 | AI 要输出**对孩子的理解**，用**词云**呈现；同时推荐美国院校，用**地图**呈现 | 个体和群体两层都要有：个体词云 + 个体地图，群体词云 + 群体地图 |
| 7 | 产品名就是 **HFI 家长成长营** | 英文名 HFI Family Growth Camp 仅用于大屏与英文界面 |

## 二、需求本质

### 一句话

> 这是一款**让家长用 3 分钟看见孩子成长方向**的 C 端产品——
> 从孩子的兴趣与特质感出发，看到这些方向通向哪些美国本科专业、哪些院校、未来几年可以怎么走。
> 线下活动是它的第一个使用场景。

### 产品的核心链条

```
孩子的兴趣 / 特质 / 自述
        ↓
  成长方向         Game Design
        ↓
 美国本科专业      Game Design · Interactive Media · CS + Design
        ↓
 这些方向通向的院校   USC · NYU · RISD · SCAD
        ↓
  美国地图上的一张分布图
```

**这条链条才是产品的本体。** 少了任何一环，产品就退化成"给孩子的性格写一段好听话"。

对家长：我孩子的兴趣，指向什么方向，这个方向对应美国哪些专业、哪些学校，可以怎么走。
对现场：这些孩子整体在往哪些方向走，这些方向通向美国的哪些地方。

### 三层拆解

| 层次 | 表面说法 | 真实诉求 | 判断标准 |
| --- | --- | --- | --- |
| 表层 | 家长能扫码填，现场能看大屏 | 参与不费劲，现场有仪式感 | 家长能不能不看说明书就走完 |
| 中层 | 用 AI 分析方向，并推荐对应的美国院校和专业 | 家长觉得"这条路我看清楚了" | 家长有没有拿这份结果去做下一步动作 |
| 本质 | 一个以"成长方向探索"为交付物的 C 端产品 | 家长愿意自己用、愿意回看、愿意分享 | 活动结束后还有没有人打开 |

### 最重要的一句判断

**产品必须回答一个问题：孩子的这个兴趣，是一个什么方向，这个方向在世界上通向哪里。**

只给"方向"不给落点，这个产品就没有存在的必要——家长随便找个 AI 聊天也能得到一段鼓励的话。
真正的价值在于：**把兴趣变成一条看得见、查得到的成长线索**，
让他知道"原来我喜欢的东西，在世界的那一头有人在做，有地方可以学"。

注意分寸：**目的是成长探索，不是升学规划。** 院校和专业是让方向"看得见"的落点，不是要去考的目标。
一旦按报考清单的方式呈现，这个产品就掉进中介赛道了。

同时因为这是 C 端产品，"家长能不能一个人顺畅走完全程"是生命线：
从扫码到拿到画像，中间不掉队、不困惑、不放弃。

原方案里最大的缺口是——它把家长当成了"数据采集的入口"，而不是"要拿东西走的人"。
所以它只写了怎么采集，没写家长拿走了什么。

**另一处需要纠正的**：地图不能只画"孩子想去哪"（家长填的志愿），
必须画"孩子的方向通向哪些学校、什么专业"（系统从兴趣特质推出来的结果）。
前者是向往，后者才是方向在现实世界里的样子。
详见 `docs/02-产品PRD.md` 3.5.2。

## 三、两条用户路径（本产品的核心结构）

```
                    ┌──────────────────────┐
                    │   孩子成长画像        │
                    │  （唯一的交付物）      │
                    └──────────▲───────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
   【路径 A】家长自助填写              【路径 B】工作人员访谈录入
              │                                 │
   手机扫码 / 分享链接 / 首页按钮        /entry（需访问口令，电脑或平板）
              │                                 │
   结构化表单 + 1 个开放题              粘贴访谈原文 → AI 抽取 → 人工核对
              │                                 │
   即时轻画像 + 短码                    结构化字段完整度更高
              │                                 │
              └────────────────┬────────────────┘
                               ▼
                    同一张表 / 同一个 AI 引擎 / 同一份画像模板
```

### 两条路径的对比

| 维度 | 路径 A：家长自助 | 路径 B：工作人员访谈 |
| --- | --- | --- |
| 使用者 | 家长本人 | 工作人员 |
| 设备 | 手机 | 电脑 / 平板 |
| 入口 | 二维码、分享链接、首页按钮 | `/entry`，需访问口令 |
| 输入方式 | 结构化表单 + chips + 1 个开放题 | 粘贴访谈原文，AI 自动抽取 |
| 目标耗时 | ≤ 90 秒 | ≤ 30 秒 / 人（不含访谈时间） |
| 数据质量 | 字段规整、信息密度低 | 信息密度高、需要人工核对 |
| 即时反馈 | 轻画像 + 短码 | 保存成功 + 短码（转交家长） |
| 使用场景 | 家长在座位/排队时自己填 | 访谈位、工作人员代录、家长不便操作时 |

### 两条路径必须统一的地方

1. **同一张表**：都写入 `children`，用 `entry_path` 字段区分来源；
2. **同一个 AI 引擎**：都不能跳过 AI 分析，画像模板完全一致；
3. **同一个出口**：都生成短码，家长凭短码回看同一份画像；
4. **字段对齐**：路径 B 抽取出来的字段必须能映射回路径 A 的表单字段，否则两类孩子的分析质量会不一致。

## 四、谁在用

| 角色 | 身份 | 核心诉求 | 技术水平 |
| --- | --- | --- | --- |
| **家长（主角）** | 活动参与者 / C 端用户 | 3 分钟填完，并且真的能拿到自己孩子的东西 | 只会扫码、用手机 |
| 工作人员 | 现场访谈与录入 | 快速录入，不打断和家长对话 | 会用电脑网页 |
| 现场观众 | 大屏前的所有人 | 一眼看懂"我们的孩子在往哪些方向走、这些方向通向哪里" | 只看 |

## 五、需求清单

### P0 · 没有它产品就不成立

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | **家长自助填写路径** | 手机优先、90 秒内完成、弱网可提交、零注册 |
| R2 | **工作人员访谈录入路径** | 粘贴原文 → AI 抽取 → 人工核对 → 保存 |
| R3 | 统一数据落库 | 两条路径进同一张表，字段对齐 |
| R4 | AI 分析引擎 | 单次调用产出：对孩子的理解 + 特质（词云）+ 3 个成长方向 + 每个方向对应的美国本科专业与院校；结构化 JSON，单条触发 |
| R5 | **院校坐标表** | 从美国教育部官方数据源（College Scorecard）**全量导入**校名 / 别名 / 州 / 经纬度，供地图打点。一期**不做**院校-专业库 |
| R6 | **孩子成长画像 + 短码回看** | C 端产品的价值交付物：3 个方向 × 对应专业 × 可去的地方 × 未来路径 |

### P1 · 决定这场活动好不好看

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R7 | 现场大屏：**美国方向地图** | 主图层：孩子的方向通向哪些院校与专业；辅图层：孩子心里想的梦想院校 |
| R8 | 现场大屏：方向与专业分布 + 群体词云 | 基于固定方向体系与固定词库 |
| R9 | 首页 | 活动入口 + 实时数据摘要，也是活动后的门面 |

### P2 · 让它变成资产

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R10 | 数据导出 | CSV / 图片化报告，交给客户留存 |
| R11 | 来源追踪 | 二维码带 `?source=`，区分海报 / 班级群 / 现场 |
| R12 | 画像分享卡 | 家长可主动生成一张不含敏感信息的画像卡片用于分享 |
| R13 | 活动复用 | 院校坐标表、特质词库、方向分类体系与代码解耦，明年只换 `data/` 下的 CSV |

### 明确不做（一期）

- **任何管理后台 / 管理页面**——当前没有运营角色，不为主办方做后台
- 批量导入**孩子数据**（Excel / CSV）
- 批量勾选操作、批量重跑界面
- 家长账号体系（手机号 / 微信登录）——一期靠短码，零门槛优先
- 录取预测、申请定位（冲刺 / 匹配 / 保底）——不做，会把这个产品拖进中介赛道
- 家长社交、社区、动态流
- 在线支付、报名费
- 公开可浏览的个体画像页
- 采集真实姓名、手机号、身份证、人脸照片

## 六、原方案的修正建议

朋友拿到的方案方向是对的（拆里程碑、先数据后页面、结构化 JSON、数据最小化都很好）。
以下 14 条是确认了"两条路径 + C 端定位"之后，我建议调整的地方：

| # | 原方案 | 问题 | 我的建议 |
| --- | --- | --- | --- |
| 1 | 用"采集 → 存储 → 分析 → 可视化"四层定义需求 | 这是实现架构，不是产品结构；现场流程与异常全没定义 | 以**两条用户路径**为主线组织需求，技术分层只作为实现手段 |
| 2 | 把家长当成"采集入口" | 只写了怎么采集，没写家长拿走了什么。C 端产品这是致命的 | **孩子成长画像是产品的本体**，采集只是第一段 |
| 3 | 家长扫码填 8–9 个字段（含 5 个开放题） | 现场填写时长过长，完成率会掉到 50% 以下 | 必填压到 4 项（英文名 / 年龄 / 梦想院校 / 1 个开放题），其余 chip 快选 |
| 4 | 工作人员录入只是一个 textarea | 访谈内容是最有信息量的数据源，原样存进去等于没用起来 | 做成"粘贴原文 → AI 抽取 → 人工核对"的结构化流程 |
| 5 | 两条路径没有统一设计 | 字段不一致会导致两类孩子的 AI 分析质量差异明显 | 抽取字段必须能映射回家长表单字段，共用同一套画像模板 |
| 6 | 梦想学校是一个下拉框 | 会逼家长在陌生校名里挑，既增加负担，又让结果失真（所有人选 Stanford） | 改成**家长自由填写**（最多 3 个，至少 1 个），输入时实时联想坐标表内的院校；命中的上图，没命中的保留原文 |
| 7 | 单孩子画像用 `/child/[id]` | 自增 ID 可被遍历，儿童信息有泄露风险 | 改为 `/child/[token]` 随机串，凭家长提交后获得的短码访问 |
| 8 | AI 实时同步分析 | 并发限制 + 现场网络波动，会出现"家长卡在转圈" | 单条异步触发 + 规则引擎降级：提交即出轻画像，AI 深度分析稍后补全 |
| 9 | 词云直接用 AI 生成的词 | 不加约束词云会炸开，无法聚合统计 | 固定 62 词词库（4 组），AI 只能从中选 8–12 个并按重要程度排序 |
| 10 | 部署到 Vercel + Supabase | 两者在国内访问都不稳定。现场 100 位家长扫码打不开就是事故 | 上线前必须用国内手机实测；备好国内服务器 + 备案域名方案；保留工作人员录入兜底 |
| 11 | 地图只回答"孩子想去哪" | 那是家长的志愿，不是方向落点。而且全体选热门校，地图会失真 | 主图层改成"孩子的方向通向哪些学校、什么专业"，梦想院校降为可切换的辅图层 |
| 12 | 让 AI 直接生成学校名和专业名 | 有杜撰风险，家长一搜可能穿帮；也没有坐标可以落图 | **一期接受这个风险**（建库要 8–15 人日，不划算），用三道低成本兜底：① Prompt 要求只写大学名、不写学院名、只推荐确定存在的组合；② 画像页标注"以学校官网为准"；③ 每所院校旁给官网搜索链接。另外配一张坐标表负责地图打点 |
| 13 | 用地图服务商的在线瓦片（如 OSM 官方瓦片） | 有使用政策风险、国内访问不稳，现场可能白屏 | 用本地 TopoJSON 画州界 + 院校点（零外部依赖）；确实要真实底图就自托管瓦片。详见 PRD 8.2 |
| 14 | 一期就想做后台 | 当前没有运营角色，做出来没人用；而数据问题真正需要解决的地方是**活动前的彩排** | 一期不做任何管理页面；把力气花在活动前用真实数据跑一遍全流程，把数据问题提前清干净 |

## 七、成功标准（可验收）

因为是对 C 产品，第一条指标就是家长端能不能走通：

| 指标 | 目标值 | 怎么量 |
| --- | --- | --- |
| 家长填写完成率 | 打开表单的人中 ≥ 85% 提交成功 | 表单埋点 start / submit |
| 单次填写耗时中位数 | ≤ 90 秒 | `started_at` → `submitted_at` |
| 画像生成成功率 | ≥ 95% | 彩排与活动前的数据核对 |
| **院校推荐准确率** | 抽检 20 条，院校名都是真实存在的美国大学、不含学院名，家长能通过官网链接查到 | 人工核对 |
| 画像打开率 | ≥ 60% 家长在 7 天内打开过回看链接 | 短码访问埋点 |
| 下一步动作率 | ≥ 30% 家长点击过画像里的院校卡片（去看地图或详情） | 点击埋点 |
| 大型展示可用 | 现场全程无空白、无报错，刷新 ≤ 30 秒 | 现场巡检 |
| 数据资产 | 活动结束 48 小时内输出 CSV + 活动报告 | 交付物清单 |

## 八、开工前必须先回答的三件事

1. **AI 推荐的准确度底线在哪？** 一期不建院校-专业库，院校和专业全部由 AI 直接推荐，
   靠 Prompt 约束 + "以官网为准" + 官网链接三道兜底。需要接受"可能有个别偏差"，
   并约定上线前的抽检标准（建议抽 20 条人工核对）。
2. **活动前什么时候彩排？** 一期没有后台，活动当天改不了数据——所有填错的、没归并上的、分析失败的，
   都必须在彩排阶段清干净。需要主办方配合，用真实数据跑一遍全流程。
3. **现场网络到底怎么样？** 自有 WiFi 还是家长用 4G/5G？能不能保证 100 人同时访问国内可达的服务器？——决定部署方案和兜底设计。

另外一条不算阻塞但值得尽早定：**一期是"一次性活动站"还是"长期可用的 C 端产品"？**
活动结束后网站还开不开放、明年还用不用同一个域名——决定要不要账号体系、要不要做留存设计。

另外一条不算阻塞但最好尽早定：**儿童数据的使用边界和知情同意文案由谁定稿。**
收集的是未成年人的成长信息，to C 产品一旦被家长质疑，风险和口碑损失都很大，建议由主办方出具正式文案。

其余细节待确认项见 `docs/02-产品PRD.md` 第 12 章。
